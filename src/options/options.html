Investigator

Add the page URL for your app under App pages. When interception is on, Investigator runs on those tabs and can take over fetch and XMLHttpRequest from the page: each matching rule either returns mock JSON you configure (optionally after a delay) or blocks the call so it fails like a network error.

You define rules that match outgoing requests—the URL (substring, regex, or glob), plus optional method, headers, or query checks. Rules run in priority order; lower numbers run first, and the first rule that matches applies to that request.

Master switch

App pages (inject here)

One origin per line — the document where your SPA runs (e.g. http://localhost:5173), not the API origin unless it is the same. Reload tabs after changing this list.

Variables

Available in any rule response JSON as {{vars.key}} (e.g. apiBase=https://api.dev → {{vars.apiBase}}).

Import from cURL

Paste a curl command. “Apply to tester” fills the rule tester; “Create rule” adds a substring rule for the URL (you can edit before Save).

Rule tester

Uses your current form values (click Save first to test saved rules). Simulates “interception on” for matching only.

Privacy & limitations

    
    
      
  • 
        Investigator runs only on origins you approve and only injects the hook scripts listed under “App pages.”
      
    • 
      
  • 
        Configuration and rules stay in chrome.storage.local on your device (not uploaded by this extension).
      
    • 
      
  • 
        Mocking applies to page main context fetch / XMLHttpRequest.
        Requests from service workers, web workers, sendBeacon, EventSource, or plain <img src> are not covered.
      
    • 
      
  • 
        Response JSON may include placeholders such as {{request.method}}, {{request.url}}, {{query.id}}, {{vars.apiBase}}, {{now.iso}}, {{now.epoch}}, {{now.ms}}.
      
    • 
      
  • 
        A rule can block a request (failed fetch / XHR error) instead of returning mock JSON.
      
    • 
    

  


  

    
    
  

    


    

    
Help

    

      Topics for how Investigator works. Settings stay in chrome.storage.local on this device.
    


    

      Getting started
      

        
    
          
  1. Add your app’s document origin under App pages (one per line), e.g. http://localhost:5173 or https://myapp.example.com.
    2. 
          
  2. Turn on Intercept requests when rules match (master switch).
    3. 
          
  3. Click Save. Approve the host permission prompt if Chrome shows it.
    4. 
          
  4. Add at least one rule that matches the API calls you want to mock or block, then Save again.
    5. 
          
  5. Reload open tabs on those origins so the injected scripts run from the start of the page.
    6. 
        

        
The toolbar icon shows a blue dot when interception is on. Use the popup for a quick on/off toggle; full editing is on this settings page.

      

    


    

      App pages — where scripts run
      

        
List the origin of the page that loads your UI (the SPA document), not necessarily the API hostname.

        
    
          
  • Example: UI at http://localhost:5173, API at http://localhost:3000 → put http://localhost:5173 in App pages. Rules can still match requests to localhost:3000.
    • 
          
  • After changing App pages, reload tabs so injection runs at document_start.
    • 
        

      

    


    

      Rules & priority
      

        
    
          
  • Enabled rules are considered; disabled rules are ignored.
    • 
          
  • Lower priority numbers run first. The first matching rule wins; remaining rules are not evaluated for that request.
    • 
          
  • Each rule must have at least one matcher among: URL pattern, method, header name, or query param name (see validation on Save).
    • 
        

      

    


    

      URL matching (substring, regex, glob)
      

        
URL pattern mode

        
    
          
  • Substring — the pattern text must appear somewhere in the target string.
    • 
          
  • Regex — JavaScript RegExp (no flags); tested with .test(...) on the target.
    • 
          
  • Glob (full string) — * matches any run of characters, ? matches one character; the whole target must match (implicit ^…$).
    • 
        

        
Match: full URL uses the resolved request URL (scheme, host, path, query, etc.). Match: path + query only uses pathname + search, so you can ignore origin when matching.

        
Relative request URLs are resolved using the page’s location (or the rule tester’s Base URL).

      

    


    

      Optional filters: method, headers, query
      

        
    
          
  • Method — if set, the request method must match (case-insensitive), e.g. POST.
    • 
          
  • Header name — if set, that header must be present. Header value contains optionally requires a substring in the header value.
    • 
          
  • Query param — if set, that query parameter must exist. Query value contains optionally requires a substring in its value.
    • 
        

        
All specified parts must pass for the rule to match the URL pattern (and URL matching still applies).

      

    


    

      Mock response: status, delay, JSON body
      

        
    
          
  • Set On match to Return mock JSON.
    • 
          
  • Response status is the HTTP statuscode callers see (e.g. 200, 404, 500).
    • 
          
  • Delay (ms) waits up to that many milliseconds before resolving (clamped to 0–120000).
    • 
          
  • Response JSON must be valid JSON. You can use templates in string values.
    • 
        

      

    


    

      Blocking requests
      

        
Set On match to Block request. The response body is ignored.

        
    
          
  • fetch — rejects with AbortError (similar to a network failure from the page’s perspective).
    • 
          
  • XMLHttpRequest — triggers the error path with status 0.
    • 
        

      

    


    

      Templates in JSON ({{…}})
      

        
In any string inside the response JSON, placeholders are replaced at mock time:

        
    
          
  • {{request.method}}, {{request.url}} — outgoing request.
    • 
          
  • {{query.paramName}} — query string value (empty if missing).
    • 
          
  • {{vars.name}} — value from Variables (one per line as name=value or name: value; lines starting with # are comments).
    • 
          
  • {{now.iso}} — UTC ISO timestamp; {{now.epoch}} — seconds; {{now.ms}} — milliseconds.
    • 
        

        
Unknown placeholders become empty strings. Templates are applied recursively through objects and arrays.

        
The Rule tester shows stored JSON only — it does not expand templates.

      

    


    

      Rule tester
      

        
    
          
  • Uses the current form values in this page (including unsaved edits). Click Save first if you want to test exactly what is stored.
    • 
          
  • Forces interception on for the dry-run only and reports the first matching enabled rule.
    • 
          
  • Enter Request URL (and optional Base URL for relative URLs), method, and header lines as Name: value.
    • 
        

      

    


    

      Import from cURL
      

        
    
          
  • Paste a command that starts with curl and includes a URL.
    • 
          
  • Apply to tester fills method, URL, and headers into the rule tester.
    • 
          
  • Create rule from cURL adds a new substring rule for the URL and method. If the command has exactly one header, it is copied into the rule’s optional header match fields for convenience — review before saving.
    • 
        

      

    


    

      Backup: export & import JSON
      

        
    
          
  • Export JSON downloads your current editor state (flush edits by tabbing through rules or Save first).
    • 
          
  • Import JSON replaces the in-memory editor from a file; you must Save to persist and refresh injected scripts.
    • 
        

      

    


    

      Console logging
      

        
When Log mocks in the page’s developer console is enabled, each matching rule writes an [Investigator] console.info line in that tab: either Mock (with HTTP status) or Block (aborted).

      

    


    

      What Investigator does not cover
      

        
Hooks run in the page’s main JavaScript world for fetch and XMLHttpRequest only. Not covered, for example:

        
    
          
  • Requests from service workers or web workers
    • 
          
  • sendBeacon, EventSource, WebSockets, or resource loads like <img src>
    • 
          
  • DevTools Network tab “real network” timing — mocks short-circuit before the browser hits the wire for matched requests
    • 
        

        
See also Privacy & limitations in the main column.

      

    


    

      Troubleshooting
      

        
    
          
  • Nothing happens — Confirm the origin is under App pages, interception is on, a rule matches, and you reloaded the tab.
    • 
          
  • Permission message — Save and approve host access; check the note under the master switch.
    • 
          
  • Wrong rule wins — Lower priority runs first; narrow patterns or split rules.
    • 
          
  • Save errors — Fix invalid JSON in a rule body, fix invalid regex patterns, and ensure each rule has at least one matcher.
    •
